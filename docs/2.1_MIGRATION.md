# Brain SDK 2.1 Migration Guide

The 2.1 release unifies all ADC ownership behind a shared `AdcEngine`. `Pots`, `Inputs`, and `AudioProcessor` no longer each configure the ADC and DMA themselves — they subscribe to ADC channels through `AdcEngine`, which owns the hardware and pushes samples back via callbacks. The result: pot reads never block, and any combination of `Pots`, `Inputs`, `AudioProcessor`, and `PotMultiFunction` can run concurrently.

## 2.1 is a non-breaking release

For most firmwares **no source changes are required**. All public APIs are source-compatible. Existing firmwares should compile and run as-is, and they automatically benefit from the new behavior (non-blocking pot reads, no init order rules).

This guide walks through the things you might want to clean up to take full advantage of 2.1, plus a small number of subtle behavior shifts to be aware of.

## You don't need to touch anything if…

…you build via `Brain` and stick to the documented API. `init_pots()`, `init_inputs()`, `init_audio_processor()`, `pots.get()`, `inputs.get_voltage_millivolts_*()`, the audio callback — all behave the same from the outside, just better.

## Things you might want to clean up

### 1. Drop the init-order workarounds

If your firmware had explicit ordering or guards around `init_audio_processor` to avoid the old "fails if pots/inputs are already initialized" rule, that defensive code can go. Init order is now flat:

```cpp
// Before — order mattered, init_audio_processor would fail
if (!brain.is_pots_initialized()) brain.init_pots(...);
brain.init_audio_processor(...);   // would fail if pots was up

// After — any order works
brain.init_pots(...);
brain.init_audio_processor(...);   // succeeds
```

### 2. Move `AudioProcessorConfig` pot tuning into `PotsConfig`

If you were tuning pot behavior through `AudioProcessorConfig`, move it to `PotsConfig`. The fields still exist on `AudioProcessorConfig` so your code compiles, but they are ignored:

| Old `AudioProcessorConfig` field | New home |
|---|---|
| `enable_pot_mux` | `PotsConfig` (just init `Pots`) |
| `pot_count` | `PotsConfig::num_pots` |
| `pot_settle_discard_samples` | `PotsConfig::settle_discard_samples` |
| `pot_average_samples` | `PotsConfig::samples_per_read` |
| `max_dma_drain_samples_per_tick` | gone — `AdcEngine` manages this |

```cpp
PotsConfig pcfg = create_default_pots_config(3, 8);
pcfg.samples_per_read = 8;        // was AudioProcessorConfig::pot_average_samples
pcfg.settle_discard_samples = 3;  // was AudioProcessorConfig::pot_settle_discard_samples
brain.init_pots(pcfg);
```

### 3. Drop the now-redundant `update_*` calls in tight loops (optional)

`pots.scan()`, `brain.update_pots()`, `brain.update_inputs()`, and `inputs.update_audio_cv()` are no-ops — `AdcEngine` keeps values fresh on its own. They are safe to leave in (they cost nothing) but you can simplify your loop:

```cpp
while (true) {
    // brain.update_pots();    // no longer needed
    // brain.update_inputs();  // no longer needed
    brain.update();            // still needed for buttons/LEDs/MIDI/etc
    uint16_t p0 = brain.pots.get(0);  // always fresh
    ...
}
```

### 4. If you build `AudioProcessor` *without* `Brain`

`Brain::init_audio_processor()` automatically calls `audio_processor.set_pots(&pots)` so pot snapshots show up in `frame->pot_raw_u8[]`. If you construct the `AudioProcessor` directly (no `Brain` wrapper) and want pot snapshots, add one line:

```cpp
Pots pots;
AudioProcessor proc;

pots.init(create_default_pots_config());
proc.set_pots(&pots);            // <-- new
proc.init(cfg, my_callback);
```

Without this, `frame->pot_count` is `0` and `proc.get_pot_raw_u8(i)` returns `0`. Calling `pots.get(i)` directly always works regardless.

## APIs that look the same but behave slightly differently

| API | Old behavior | New behavior |
|---|---|---|
| `pots.get_raw(i)` | Forced a fresh hardware read | Returns the latest cached averaged sample |
| `pots.get_single(i)` | Forced a fresh hardware read, mapped to output resolution | Returns the latest cached value, identical to `pots.get(i)` |
| `pots.scan()` | Sampled all pots and updated buffers | No-op (buffers are always current) |
| `inputs.update_audio_cv()` | Refreshed cached A/B values | No-op |
| `pots.set_simple(true)` | Switched to a faster, noisier read path | No effect — only one DMA path exists |
| `pots.set_settling_delay_us(n)` | Changed mux-settle wait | No effect — settling is handled by `settle_discard_samples` |

In every case the new behavior is a strict improvement (fresher data, no blocking, no jitter from settle waits). If you were using these APIs to "force a fresh value" before reading, you can drop the call — the value is already fresh.

## Legacy no-op shims

These methods still exist for source compatibility but have no runtime effect:

- `Brain::enable_adc_optimization(bool)`
- `Brain::set_audio_cv_dma_enabled(bool)`
- `Brain::set_shared_pot_sampling_enabled(bool)`
- `Pots::set_simple(bool)`
- `Pots::set_optimized_sampling_enabled(bool)`
- `Pots::is_optimized_sampling_enabled()` — always returns `true`
- `Pots::set_settling_delay_us(uint32_t)`
- `Pots::scan()`
- `Inputs::set_audio_cv_dma_enabled(bool)`
- `Inputs::is_audio_cv_dma_enabled()` — always returns `true`
- `Inputs::is_audio_cv_dma_active()` — returns whether `init_audio_cv()` succeeded
- `Inputs::update_audio_cv()`

These are safe to keep in your code. Newly written code should prefer the unified API (`pots.get(i)`, `inputs.get_raw_*()`, etc.).

## Audit checklist

For each existing firmware:

- [ ] Search for `init_audio_processor` and remove any init-order defensive logic.
- [ ] Search for `AudioProcessorConfig` and move pot tuning fields into `PotsConfig`.
- [ ] If you ever called `proc.init(...)` directly (not via `Brain`), add `proc.set_pots(&pots)` if you want pot snapshots.
- [ ] Compile. If it builds, you are done.

## Why this changed

Before 2.1, three components each owned their own ADC + DMA configuration: `Pots` did blocking ADC reads with `busy_wait_us_32`, `AudioProcessor` ran its own DMA + round-robin and demuxed pot samples in software, and `Inputs` had a separate DMA path. Because they all needed the same hardware, mixing them was illegal — `init_audio_processor` failed if `init_pots` had succeeded, and vice-versa.

2.1 introduces `AdcEngine`: a singleton that solely owns the ADC, DMA, ring buffer, and round-robin scheduling. Components subscribe to ADC channels via callback; `AdcEngine` demuxes and dispatches samples. This eliminates blocking pot reads (a ~500 µs stall per scan in the old path), eliminates the cross-component init-order rules, and removes ~200 lines of duplicate ADC setup spread across the three components.
