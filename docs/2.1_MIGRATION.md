# Brain SDK 2.1 Migration Guide

The 2.1 release rewrites the ADC and DAC plumbing under the hood while keeping the public API source-compatible with 2.0. Most firmwares need **zero code changes**. The migration is mostly about understanding what stopped being a constraint, and one new API surface (stereo audio) you can opt into when you want it.

If you maintain firmware code or you're an AI agent migrating one, this guide is what you need.

## TL;DR

For most firmwares: bump the submodule, rebuild, you're done.

The two things that meaningfully changed:

1. **`AudioProcessor` no longer conflicts with `Inputs`, `Pots`, or `PotMultiFunction`.** They all share the same internal ADC engine now and you can initialize any combination on one `Brain` instance. Anywhere your code used to handle the failing init or design around the conflict — that workaround is dead code now.
2. **There's a new optional v2 API for stereo audio** (`init_audio_processor_v2` + `ProcessFrameFnV2`) that gives you both inputs (IN1, IN2) and both outputs (OUT A, OUT B) in one DSP callback. The legacy single-channel API (`init_audio_processor` + `ProcessSampleFn`) keeps working unchanged.

That's it. The rest of this document explains the why and the smaller details.

## What changed under the hood

Brain 2.1 introduces two internal "engines" that own the hardware exclusively:

- **`AdcEngine`** — sole owner of the ADC. Continuously samples (POT, IN1, IN2) in round-robin via DMA. `Inputs` and `Pots` are now thin readers over its snapshots. When `AudioProcessor` is active the engine switches into a per-sample IRQ mode at the configured audio rate.
- **`OutputEngine`** — sole owner of the DAC. Streams 16-bit MCP4822 frames into the SPI peripheral via a single ring-DMA channel paced by a hardware timer. On RP2350 the channel runs in `ENDLESS` mode — the engine streams forever in hardware with **zero IRQs and zero CPU work** until something writes a new value. On RP2040 it auto-runs for ~14 hours per cycle.

Both engines are singletons. All public components (`Inputs`, `Pots`, `PotMultiFunction`, `Outputs`, `AudioProcessor`) sit on top of them. That's why coexistence is now free — they're not competing for hardware, they're sharing it.

The legacy `AudioProcessor` had its own private ADC DMA, its own SPI bus access for the DAC, and a periodic timer running the DSP. All of that is gone. The new `AudioProcessor` is a thin shim that:

- Switches `AdcEngine` into audio mode at the requested sample period.
- Claims one or both `OutputEngine` channels as audio-owned.
- Registers a callback that fires from the ADC's per-sample IRQ at audio rate (~43 kHz at the default 23 µs).

The wire-level audio quality and timing are equal to or better than 2.0.

## What is **not** a breaking change

- All `Brain::*` init/update calls work identically.
- All component public APIs (`Inputs`, `Pots`, `PotMultiFunction`, `Outputs`, `Leds`, `Buttons`, `MidiParser`, `MidiToCv`, `Storage`) work identically.
- `AudioProcessor::init`, `ProcessSampleFn`, `AudioProcessorConfig`, `AudioProcessorFrame`, `AudioProcessorStats`, `get_pot_raw_u8`, `get_stats`, and `stop` all work identically.
- `AudioProcessorConfig::sample_period_us` default is still `23` (~43.5 kHz audio rate).
- `BRAIN_USE_*` flags are unchanged.
- `BrainInitStatus` values are unchanged.

## What changed from a calling-code perspective

### Conflict guards are gone

In 2.0, these calls would return `kBrainInitStatusFailed` if `AudioProcessor` was initialized:

- `brain.init_inputs()`
- `brain.init_pots(...)`
- `brain.reconfigure_pots(...)`
- `brain.init_pot_multi(...)`

And conversely, `brain.init_audio_processor(...)` would fail if any of the above were already initialized.

In 2.1, all six of those calls succeed regardless of order. You can now write firmware that uses `AudioProcessor` and `Pots` and `Inputs` in the same `Brain` instance.

If your code had error-handling branches for these specific failures, those branches are now unreachable. You can delete them (recommended), or leave them as defensive code (harmless).

### `AudioProcessorConfig::max_dma_drain_samples_per_tick` is ignored

The legacy `AudioProcessor` had its own internal DMA ring and used this field as a per-tick safety bound. The new architecture has no such ring — input samples come straight from the IRQ callback. The field is preserved in the struct so old code compiles without changes, but its value is ignored. Safe to leave or delete.

### `AudioProcessorConfig::spi_baud_hz` is ignored

The DAC's SPI baud is owned by `OutputEngine` and fixed at 20 MHz. This field is preserved for source compat but ignored. Safe to leave or delete.

### `PotsConfig::channel_map` is now ignored

Brain hardware always wires pot N to mux channel N. The remap layer existed for hypothetical board variants and is gone. The field stays in `PotsConfig` for source compatibility (so existing config initializers still compile) but `AdcEngine` ignores it. The field carries `[[deprecated]]`, so any callsite that touches it will surface a compile warning. Safe to delete from your config initializers.

If you previously relied on a non-identity `channel_map` to remap logical pot indices, that remap was already broken in 2.1 (the index was applied twice). On Brain hardware the only correct mapping is the identity one, which the engine now hardcodes.

### `OutputEngineSnapshot` adds new fields

If you read `OutputEngine::instance().get_snapshot()` directly (most firmware doesn't — it's an internal API), the snapshot struct gained `audio_overflow_a` / `audio_overflow_b` diagnostic counters and dropped `audio_frame_a` / `audio_frame_b` (the engine no longer caches a single audio frame).

### `adc-arbiter.h` is gone

If you `#include "brain/include/adc-arbiter.h"` anywhere — remove it. It was an internal header used only by the legacy `AudioProcessor`'s ADC DMA path. The class `BrainAdcLockGuard` no longer exists. There are no consumers of it in any normal firmware.

## What's new

### Stereo audio (v2 API)

For firmware that wants both inputs and both outputs in the audio loop:

```cpp
#define BRAIN_USE_AUDIO_PROCESSOR 1
#include "brain/brain.h"

Brain brain;

static void process_stereo(int16_t in1, int16_t in2,
                           const AudioProcessorFrameV2* frame,
                           int16_t* out_a, int16_t* out_b,
                           void* user_ctx) {
    // Simplest example: stereo passthrough.
    *out_a = in1;
    *out_b = in2;
}

int main() {
    AudioProcessorConfigV2 cfg{};
    cfg.sample_rate_hz = 43500;       // explicit sample rate (replaces sample_period_us)
    cfg.enable_pot_mux = true;        // pots scanned alongside audio (no conflict)
    cfg.pot_count = 3;
    cfg.claim_channel_a = true;
    cfg.claim_channel_b = true;       // claim both outputs

    if (!brain_init_succeeded(
        brain.init_audio_processor_v2(cfg, process_stereo, nullptr))) return 1;

    while (true) { /* ... */ }
}
```

You can also opt into v2 with only one channel claimed (e.g. `claim_channel_b = false`) — useful if you want the v2 callback shape (with both inputs available) but only need to write one output channel.

### Coexistence

Any combination of components works on one `Brain` now:

```cpp
brain.init_audio_processor(cfg, process, ctx);
brain.init_inputs();           // OK
brain.init_pots();             // OK
brain.init_pot_multi();        // OK
brain.init_outputs();          // OK — but channel A (claimed by audio) refuses set_voltage_*
```

Order doesn't matter. All components share the underlying engines.

One subtle point: when `AudioProcessor` claims an output channel as audio, manual writes to that channel via `Outputs::set_voltage_*` return `false` (no-op) until `AudioProcessor::stop()` releases it. This is the *only* runtime constraint between components.

### Audio claims force channels into bipolar (-5..+5 V) range

`AudioProcessor` writes signed samples around 0, so claiming a channel for audio drives its coupling pin high — equivalent to a `Outputs::set_output_range(channel, kRangeMinus5To5V)`.

**`AudioProcessor::stop()` does not restore the prior range.** Two things to be aware of:

- The coupling pin stays **high** (bipolar) after `stop()`.
- `Outputs::range_a_ / range_b_` still hold whatever they were before — by default `kRange0To10V` (unipolar). That means the next `Outputs::set_voltage_*` call will compute its DAC value assuming unipolar but the hardware is configured bipolar — the voltage you read on the jack won't match the millivolts you asked for.

If your firmware uses a claimed channel for manual writes after `stop()`, call `Outputs::set_output_range(channel, ...)` first. That re-syncs the coupling pin with `Outputs`'s internal state, and subsequent `set_voltage_*` calls produce the right voltage. Firmwares that don't touch the channel after `stop()` are unaffected.

## Migration checklist

For each firmware project you're updating:

1. **Update the `pico-sdk` and `brain-sdk` submodules** to the 2.1 versions.
2. **Rebuild.** Typical project: no source changes needed.
3. **Search your code for `BrainAdcLockGuard`** and `#include "brain/include/adc-arbiter.h"`. Delete both. These were only used by the legacy `AudioProcessor`'s internals; if your firmware was using them, it was reaching into private territory.
4. **Search your code for fail-paths** around `init_audio_processor`, `init_inputs`, `init_pots`, `init_pot_multi`. Specifically the pattern "fail if the other is initialized" — that case can no longer happen. Either delete the dead branch or leave it; both are correct.
5. **Optional: remove `max_dma_drain_samples_per_tick` and `spi_baud_hz`** from your `AudioProcessorConfig` initializers. They're ignored. Cosmetic.
6. **Optional: try the v2 API** if you want stereo audio or want both inputs available in one DSP callback.
7. **Re-test on hardware.** The audio path was rewritten end-to-end, so even if your firmware compiles unchanged, run a quick listen test on any audio-related app.

## Behavior differences worth noticing

These aren't breaking but are useful to know:

- **Audio is now sample-locked to the ADC.** The DAC's frame timer and the ADC's clock divider are derived from the same crystal-PLL chain, with the math arranged so the rates match exactly. There's no slow drift between the input and output sample rates anymore — what used to manifest as a faint periodic artifact at long-running sample rates is gone.
- **`OutputEngine` produces clean per-sample audio.** In 2.0, audio output was effectively held for 16-frame blocks at the DAC level (a deliberate design constraint of the previous architecture). In 2.1, every audio sample reaches the DAC distinctly at the configured rate.
- **CV-mode CPU is lower.** When `AudioProcessor` is *not* in use, the engines run with minimal IRQ activity (one short ADC IRQ every ~192 µs). On RP2350 the DAC engine has zero IRQs in `kManual`-only mode.
- **Multiple `Brain` instances no longer interfere.** Test code that creates multiple `Brain` objects — for example to verify behavior across hypothetical configurations — used to clobber the singleton engines because the `AudioProcessor`'s destructor unconditionally tore the shared state down. The 2.1 destructor is a no-op when the instance never claimed anything, so unrelated `Brain` lifetimes are now safe.

## Questions or unexpected behavior?

If you hit a runtime issue that wasn't there in 2.0:

- Check `brain.audio_processor.get_stats()` for `overrun_count`. If it's growing while audio is running, your DSP is taking longer than the configured sample period. Reduce work or increase `sample_period_us`.
- For stereo audio: check `OutputEngine::instance().get_snapshot()` for `audio_underrun_a/b` and `audio_overflow_a/b`. With matched rates these stay at 0; if either climbs, something is unusual about your setup.
